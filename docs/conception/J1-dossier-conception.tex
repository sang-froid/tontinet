\section{Objet et hypothèses}

Ce dossier fixe l'architecture de TontiNet, le mécanisme de communication de chaque échange, le
format des messages et la sémantique d'appel de chaque opération ; il sert de contrat entre
l'équipe serveur et l'équipe mobile. Les identifiants RG, EF, SEC et ADR renvoient au cahier des
charges [CDC], les numéros de leçon aux notes de cours [NC]. Nous supposons des pannes par arrêt
ou par omission : trois répliques en tolèrent une ($n = 2f + 1$, $f = 1$). Le réseau est
asynchrone, donc chaque appel porte un délai d'attente, et l'heure du téléphone n'ordonne jamais
rien (RG16). Principe directeur, issu du théorème CAP : \textbf{la collecte est AP, le versement
est CP}.

TontiNet combine les trois styles du cours [NC 1.2.1] : \textbf{client-serveur} entre les
terminaux et l'API, \textbf{réplication entre pairs} entre les répliques,
\textbf{publication/abonnement} pour les notifications (\figref{fig:architecture}). L'application
Flutter fonctionne \emph{hors connexion d'abord}. Toute réplique accepte une cotisation (chemin
AP : \textbf{G-Set indexé par l'UUID}, copie sur un pair, anti-entropie) ; paramètres,
bénéficiaires et sagas passent par un \textbf{journal Raft} dont seul le leader propose les
entrées (chemin CP). Le versement est une saga orchestrée par le leader (T1 geler, T2 débiter,
T3 créditer, T4 clore ; compensations C2 puis C1). Les notifications passent par une \emph{outbox}.

\section{Format des messages}
\label{sec:format}

L'API publique (\texttt{/v1}) échange du JSON UTF-8 : champs en français sans accent, montants
\textbf{entiers} en francs CFA, cotisation identifiée par un \textbf{UUID créé sur le téléphone},
dates ISO 8601 UTC (\texttt{saisie\_le} reste indicatif). L'en-tête \texttt{X-Request-Id} suit la
requête de REST à gRPC puis à MQTT.

\begin{lstlisting}[numbers=none, caption={Enregistrer une cotisation : requête puis réponse}, label={lst:rest}]
PUT /v1/cotisations/7f3c2a9e-5b1d-4c8e-9a21-0d4e5f6a8b90
{"tontine": "femmes-zogbo", "tour": 3, "membre": "M07",
 "montant": 2000, "collecteur": "C1",
 "saisie_le": "2026-11-21T09:14:03Z"}
200 OK {"id": "7f3c2a9e-...", "doublon": false,
        "solde_tour": 14000, "replication": "quorum"}
\end{lstlisting}

\texttt{replication} vaut \texttt{degradee} si une seule réplique a pu écrire : le téléphone
renvoie alors la cotisation, sans risque, jusqu'à obtenir \texttt{quorum}. Les erreurs suivent la
RFC 9457 avec un \texttt{code} stable (\texttt{ID\_CONTENU\_DIFFERENT}, \texttt{TOUR\_VERSE},
\texttt{PAS\_DE\_MAJORITE}\ldots). Le curseur de \texttt{GET /v1/sync} est un vecteur de
versions par réplique d'origine (ADR-07). Entre répliques, le contrat Protobuf fait foi :

\begin{lstlisting}[language=Protobuf, caption={Extrait du contrat \texttt{proto/tontinet/v1/}}, label={lst:proto}]
message Cotisation {
  string id = 1;  string tontine = 2;  int32 tour = 3;
  string membre = 4;  int64 montant = 5;  string collecteur = 6;
  string saisie_le = 7;  string recue_par = 8;
  reserved 9 to 15;                  // numéros jamais réutilisés
}
service Replication {                // mTLS, deadline 2 s
  rpc Repliquer(Lot) returns (Accuse);         // écriture W = 2
  rpc Comparer(Resume) returns (Resume);       // anti-entropie
  rpc Recuperer(Resume) returns (stream Cotisation);
}
service Coordination {               // suiveur → leader
  rpc Transmettre(CommandeCP) returns (ResultatCP);
}
\end{lstlisting}
